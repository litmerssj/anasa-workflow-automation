# LOG 백로그 3분할 배정 설계

## 목적

현재 Anasa의 활성 LOG 티켓 중 개발 가능한 전체 백로그를 Ian, Jin, Roger에게 동일하게 나누고 곧바로 처리하게 한다. 기존 WIP 3건 제한은 이후 새 티켓 운영에는 유지하되, 이번 LOG 백로그 일괄 분배에는 적용하지 않는다.

## 대상

- 제목이 `[LOG]`로 시작한다.
- 상태가 완료 또는 취소가 아니다.
- `고객확인`, `QA대기`, `QA중`, `최종검수대기`, `검수요청` 라벨이 없다.
- 현재 실측 대상은 126건이며, 고객 답변 대기 4건은 제외한다.
- Tier 라벨이 없는 현장미팅 개발 티켓 34건도 포함한다.

## 분할 규칙

- 정렬 기준은 Linear 이슈 번호 오름차순으로 고정한다.
- Tier 3를 먼저 Ian에게 넣은 뒤 나머지를 번호순으로 채워 Ian 42건, Jin 42건, Roger 42건을 만든다.
- 각 티켓에 기계 판독 가능한 계획 코멘트를 남겨 재실행해도 같은 담당자가 유지되게 한다.
- 이미 이 일괄 작업의 계획 코멘트가 있는 티켓은 계획을 다시 계산하지 않는다.

## 적용 시점

- Ian과 Jin은 활성 Linear 멤버이므로 계획 생성 직후 각각 42건을 실제 담당자로 지정한다.
- Roger는 아직 초대 수락 전이므로 42건의 계획만 먼저 고정한다. 활성 멤버가 된 다음 워커 패스에서 예약된 42건 전체를 실제 담당자로 지정한다.
- Roger 몫은 대기 중 Ian이나 Jin에게 재분배하지 않는다.

## 기존 자동배정과의 관계

- 이번 126건에는 `log_backlog_planned` 이벤트를 남기고 일반 WIP 자동배정 대상에서 제외한다.
- 초대 수락 전 사용자 때문에 활성 개발자의 배정까지 전부 막히던 전역 게이트는 제거한다.
- 일반 신규 티켓은 활성 개발자만 대상으로 기존 WIP 3건 제한과 최소 부하 규칙을 계속 적용한다.
- Tier 3는 계속 Ian만 담당한다. 일괄 분할 대상의 Tier 3를 Ian에게 먼저 넣고 나머지 티켓으로 각 묶음을 채우므로 총량은 정확히 42/42/42다.
- QA 풀 활성 여부는 개발자 배정을 막지 않으며, QA는 활성 QA 담당자만 사용한다.

## 실패·재실행

- 이슈별 업데이트와 코멘트 실패를 기록하고 나머지 티켓 처리는 계속한다.
- 계획 코멘트가 먼저 기록된 뒤 담당자 업데이트가 실패하면 다음 패스가 같은 계획을 재사용해 복구한다.
- 실제 담당자와 고정 계획이 다르면 고정 계획을 기준으로 복구한다.

## 검증

- 단위 테스트에서 126건이 42/42/42로 고정되고 비활성 Roger 몫은 예약만 되는지 확인한다.
- 운영 적용 후 Ian 42건, Jin 42건, Roger 예약 42건, 고객확인 제외 4건을 API로 재집계한다.
- Roger 수락 후 예약 42건이 전부 실제 배정되는지 확인한다.
