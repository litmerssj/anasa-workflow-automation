# 아나사 고객 보드 (ANACO-2 v1)

Linear를 원장(SSOT)으로 쓰는 **번역층**. 자체 DB 없음 — 모든 조회는 매 요청 Linear GraphQL API를 직접 호출한다.

## 화면 3개

| 경로 | 용도 |
|---|---|
| `/` | 고객 보드 — 인테이크 폼 + 질의 레인(질의대기/회신완료/반영됨) + 검수 레인(검수요청/재수정요청) |
| `/viewer` | 레퍼런스 뷰어 — 화면코드 검색 → 설계서 이미지 (라이브 스크린샷은 v2 예정) |
| `/internal` | 내부 운영 큐 — 고객 회신 판정, AI 질의초안 검토·공개, 같은 티켓의 QA·최종검수 처리 |

## 실행 전 필요한 것

```bash
cp .env.example .env.local
```

```bash

```

## 상태 판정 로직 (읽어두면 좋음)

개발·내부 QA는 Linear 상태 `Backlog → In Progress → QA Request → QA In Progress → Done`을 단일 원장으로 사용한다. 고객 질의 레인은 기존 라벨 조합을 유지한다.

- **질의 레인**: 라벨 `고객확인`(현재 블록) + `질의이력`(영구 마커) 조합으로 판정.
  - `질의이력` 있고 `고객확인` 있음 + 마지막 코멘트가 `**[답변]**`으로 시작 → **회신완료**
  - `질의이력` 있고 `고객확인` 있음, 아직 답변 없음 → **질의대기**
  - `질의이력`은 있는데 `고객확인`이 없음(제거됨) → **반영됨**
  - ⚠️ **감사셀이 티켓에 질의를 걸 때는 `고객확인`과 `질의이력` 라벨을 반드시 함께 부착해야 한다.** 라벨을 직접 관리하거나 `/internal`의 "재질의" 버튼을 사용한다. 버튼을 쓰면 두 라벨이 함께 붙는다.
- 기존 `검수요청` / `검수반려` 레인은 과거 데이터 읽기 호환만 유지한다. 신규 고객 피드백은 새 Linear 티켓으로 등록한다.
- 카드 위 질문 본문은 코멘트를 파싱한다. 새 코멘트는 `**[질의]**` 접두와 마지막 줄 `선택지(JSON): ["A","B"]`를 사용한다. 선택지 안의 쉼표가 깨지지 않도록 JSON이 표준이며, 기존 `선택지: A, B`도 읽기 호환만 유지한다.
- Linear가 댓글을 최신순으로 반환하므로 질문·답변·반려 사유는 배열 위치가 아니라 `createdAt` 기준 최신 댓글을 사용한다.
- `QA Request`와 `QA In Progress` 상태가 없으면 워커는 안전하게 실패하고 상태 프로비저닝을 요구한다.

## 개발자-AI 티켓 처리 원칙

- 고객 보드의 ERP·ORD 요청은 별도 재발 유형을 고르게 하지 않고 `고객보드`와 `자동분류-미확정` 라벨의 단일 티켓으로 접수한다.
- `자동분류-미확정`은 ORD 전용 또는 재발 판정 라벨이 아니다. ERP·ORD 공통으로 티어를 확정하기 전 사용하는 안전 상태다.
- 워커는 자동 진단 후 Tier를 확정한다. 결정적인 SQL/SP·공유 DB 쓰기·일괄 데이터 변경·인증/권한/보안 경계만 Tier 3로 Core에 보내고, 나머지는 Anasa에 둔다.
- Tier 1을 포함한 모든 수정 티켓은 개발자에게 자동 배정한다. 코드 자동수정은 하지 않으며 담당 개발자가 AI 코딩 에이전트로 처리한다.
- 개발자가 질문을 남기면 AI가 고객용 폐쇄형 질문으로 변환한다. 안전한 질문은 자동 공개하고 계약·일정·책임·보안 판단은 `/internal` 검토 후 공개한다.
- 개발 완료 시 같은 티켓을 `QA Request`로 전환한다. QA 담당자는 즉시 자동 배정되지만 상태는 유지하며, 실제 착수할 때 `QA In Progress`로 직접 변경한다.
- 내부 QA 통과는 `Done`, 반려는 원 개발자에게 재배정 후 `In Progress`다.
- 고객 전달은 모듈·마일스톤 단위 `[최종검수]`로 관리한다. 이후 고객 피드백은 기존 완료 티켓을 다시 열지 않고 `Bug` 또는 `Change Request` 새 티켓으로 접수한다.
- AI 코딩 에이전트는 화면코드와 증상 키워드로 관련 과거 티켓을 찾아 구현 및 회귀 테스트의 문맥으로 참고할 수 있다.
- 관련 티켓 검색 결과만으로 재발을 자동 판정하거나 티켓을 합치고 닫지 않는다. 재현·수정·검증은 현재 티켓 단위로 끝낸다.

## 알려진 v1 한계 (의도적 스코프 절단, 은닉 아님)

1. **레퍼런스 뷰어 라이브 스크린샷 없음** — 설계서 이미지만 있음. 스윕 하니스가 매일 밤 화면별 스크린샷을 안정적 경로에 저장하도록 확장하면 다음 버전에서 연결.
2. **QA 증빙은 개발완료 코멘트 컨벤션 의존** — `PR/커밋`, `스모크`, `수정 전`, `수정 후` 네 항목이 없으면 QA 통과를 차단한다.
3. **`/internal`은 공유 비밀번호 + 서명된 HttpOnly 세션** — 인원이 늘면 Linear OAuth 같은 개인 인증으로 교체한다.
4. **화면 선택기의 화면코드가 정확한 라우트에 안 걸려있음** — 화면코드(예: PDT-OSC-002M)만 저장하고 실제 FE 라우트 slug와는 아직 안 이어져 있음. `erp2 딥링크`는 향후 `screen-manifest.json` 매핑 작업 필요.
