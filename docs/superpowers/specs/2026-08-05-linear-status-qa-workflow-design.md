# Linear 상태 기반 QA 워크플로우 설계

## 1. 목표

Anasa 티켓의 개발·내부 QA 진행 상황을 Linear 상태만 보고 이해할 수 있게 한다. `Done`을 개발 완료 신호로 잠깐 사용한 뒤 `In Progress`로 되돌리는 기존 우회 전이를 제거한다.

개별 개발 티켓의 최종 상태 흐름은 다음과 같다.

```text
Backlog → In Progress → QA Request → QA In Progress → Done
```

`Done`은 해당 티켓의 내부 QA 통과를 뜻한다. 고객 검수는 개별 티켓 상태로 관리하지 않는다.

## 2. 상태 정의

| 상태 | Linear 유형 | 의미 | 담당자 |
|---|---|---|---|
| `Backlog` | Backlog | 분류·배정 전 작업 | 미배정 또는 계획 담당자 |
| `In Progress` | Started | 개발자가 구현·수정 중 | 개발자 |
| `QA Request` | Started | 개발 완료, QA 담당자 배정 완료 또는 배정 대기, QA 미착수 | 배정된 QA 담당자 |
| `QA In Progress` | Started | QA 담당자가 실제 검수를 수행 중 | QA 담당자 |
| `Done` | Completed | 내부 QA 통과 | 마지막 QA 담당자 |

기존 `Todo`는 삭제하지 않지만 신규 자동화에서는 사용하지 않는다. `Canceled`와 `Duplicate`도 현재 의미를 유지한다.

## 3. 전이 규칙

### 개발 완료

개발자는 구현·증빙 준비가 끝나면 원 티켓을 `In Progress`에서 `QA Request`로 변경한다. `Done`을 중간 신호로 사용하지 않는다.

Webhook 또는 5분 polling 워커는 `QA Request` 진입을 감지해 다음 작업을 수행한다.

1. 최신 `dev_assigned` 이벤트에서 원 개발자를 보존한다.
2. 증빙 요건을 확인한다.
3. WIP 규칙에 따라 QA 담당자를 자동 배정한다.
4. `qa_assigned` 구조화 코멘트를 남긴다.
5. 상태는 `QA Request`로 유지한다.

### QA 착수

QA 담당자가 실제 검수를 시작할 때 티켓 상태를 직접 `QA In Progress`로 변경한다. 담당자 배정만으로 상태를 자동 변경하지 않는다.

### QA 통과

QA 통과에는 PR 또는 커밋 링크, 스모크 결과, 수정 전·후 증빙이 필요하다. 요건을 만족하면 `**[QA:통과]**` 코멘트를 남기고 상태를 `Done`으로 변경한다.

### QA 반려

QA 담당자는 반려 사유를 필수로 남긴다. 워커는 `**[QA:반려]**` 코멘트를 기록하고 최신 `dev_assigned` 이벤트의 원 개발자에게 재배정한 뒤 상태를 `In Progress`로 변경한다. 별도 반려 상태나 새 티켓은 만들지 않는다.

## 4. 고객 전달과 피드백

고객은 개별 개발 티켓을 검수하지 않는다. 윤아와 승현이 모듈 또는 마일스톤 단위의 `[최종검수]` 총괄 티켓으로 큰 단위 검수를 마친 뒤 고객에게 전달한다.

따라서 개별 티켓에는 `Customer Review`, `Changes Requested`, 고객 반려 상태를 추가하지 않는다. 기존 티켓의 `Done`도 고객 피드백 때문에 다시 열지 않는다.

고객 전달 후 나온 피드백은 새 티켓으로 `Backlog`에 등록한다.

- 현장 미팅에서 나온 피드백은 `현장인터뷰` 출처 라벨을 붙인다.
- 고객보드로 접수된 피드백은 `고객보드` 출처 라벨을 붙인다.
- 기존 요구 범위의 결함이면 `Bug`, 새로운 요구나 범위 변경이면 `Change Request`로 분류한다.
- 화면코드, 관련 기존 티켓, 해당 `[최종검수]` 총괄 티켓을 관계 링크 또는 본문에 기록한다.

## 5. 라벨 정리

`QA대기`와 `QA중`은 더 이상 상태 제어에 사용하지 않는다. 기존 티켓 이력 보존을 위해 즉시 삭제하지 않으며, 활성 티켓을 새 상태로 마이그레이션한 뒤 자동화에서만 제거한다.

- `QA대기` 활성 티켓 → `QA Request`
- `QA중` 활성 티켓 → `QA In Progress`
- 내부 QA 반려 출처는 `**[QA:반려]**` 코멘트로 보존한다.
- `검수요청`·`검수반려`는 신규 개별 티켓 워크플로우에서 사용하지 않는다.
- `[최종검수]` 총괄 티켓과 `최종검수` 라벨은 모듈 단위 검수용으로 유지한다.

## 6. 자동화 변경 범위

다음 동작을 함께 변경한다.

1. Linear 팀에 `QA Request`, `QA In Progress` 상태를 Started 유형으로 추가한다.
2. `Done` 감지 후 `In Progress + QA대기`로 되돌리는 Webhook·polling 로직을 제거한다.
3. `QA Request` 진입을 QA 배정 트리거로 사용한다.
4. QA 배정 후 상태를 바꾸지 않는다.
5. QA 통과는 `Done`, QA 반려는 `In Progress`로 전이한다.
6. WIP 계산에서 `QA Request`와 `QA In Progress`를 개발 WIP에서 제외하고 QA WIP에 포함한다.
7. 고객보드 내부 QA 화면은 상태 기반으로 큐를 조회한다.
8. 기존 활성 `QA대기`·`QA중` 티켓을 새 상태로 일회성 마이그레이션한다.

## 7. 안전 장치

- 두 QA 상태가 Linear에 존재하지 않으면 워커는 상태 전이를 시도하지 않고 명확한 오류를 남긴다.
- QA 담당자 계정이 유효하지 않거나 WIP 상한에 도달하면 티켓은 `QA Request`에 그대로 남는다.
- Webhook과 polling은 같은 멱등 전이 함수를 사용해 중복 배정·중복 코멘트를 막는다.
- 고객 피드백 신규 티켓은 기존 완료 티켓을 자동 재개하거나 중복으로 판정하지 않는다.

## 8. 검증 기준

1. `In Progress → QA Request`에서 QA 담당자가 배정되지만 상태는 유지된다.
2. QA 담당자가 수동으로 `QA In Progress`로 변경할 수 있다.
3. 증빙이 완전한 QA 통과는 `Done`이 된다.
4. 증빙 누락 시 `Done` 전이가 거부된다.
5. QA 반려는 원 개발자에게 돌아가고 `In Progress`가 된다.
6. 개발자가 `Done`을 눌러도 기존의 자동 재오픈 전이가 발생하지 않는다.
7. 기존 `QA대기`·`QA중` 활성 티켓이 각각 새 상태로 정확히 이동한다.
8. 모듈 단위 `[최종검수]` 총괄 티켓은 유지되고 개별 완료 티켓은 고객 피드백으로 재개되지 않는다.
